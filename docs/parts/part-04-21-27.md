# PROJECT 1864 — Designmanual v00.02.00 — Del 4

## 21. Strategisk AI

Strategisk AI skal arbejde med mål og constraints snarere end scripts. Historiske planer bruges som priors og scenario guidance, men AI må kunne reagere på alternative situationer.

- National AI: war goals, risk tolerance, diplomacy, mobilisation og theatre priorities.
- Theatre AI: defend objectives, concentration, supply feasibility, reserves, operational axes og enemy estimates.
- Army AI: march, screening, engagement thresholds, withdrawal og pursuit.
- AI skal kende sin egen fog of war og må ikke bruge spillerens skjulte oplysninger.
- AI-planer bør kunne inspiceres i debug/telemetry for at gøre balance mulig.

## 22. Taktisk AI

Taktisk AI er hierarkisk. En brigadechef får mission og intent, vælger sectors og reserve; regiment/bataljon udfører formation og local combat. Dette er både mere realistisk og mere performant end tusindvis af selvstændige agents.

| Niveau | AI-ansvar |
| --- | --- |
| Battle commander | Overordnet plan, reserves, main effort, retreat threshold. |
| Division | Sektorer, brigade missions, artillery priorities, timing. |
| Brigade | Regimental/battalion positions, local reserves, flank reaction, counterattack. |
| Regiment/Battalion | Formation, facing, micro-route, fire control, cover use, local retreat. |
| Visual soldiers | Animation slots og local avoidance; ingen strategisk beslutnings-AI. |

## 23. 3D-slagmarker og terrængenerering

Der bør anvendes en hybrid mellem håndlavede historiske nøgleslag og proceduralt genererede/komponerede generiske områder. Dybbøl og andre ikoniske steder fortjener håndverificerede maps; mindre encounters kan bygges dynamisk fra strategiske geo-lag.

- Terrain tiles baseret på elevation/landcover kan sammensættes deterministisk efter world coordinates.
- Roads, streams, settlements og woods skal følge strategikortets data, så operationelle valg kan genkendes taktisk.
- Historiske landmark overrides kan erstatte genererede elementer i nøgleområder.
- Battle boundary skal være stor nok til flankering og retreat, men ikke så stor at traversal bliver meningsløs.

## 24. Grafik, animation og performance

Målet er store formationer, ikke individuel soldier simulation som i et actionspil. Performance-budgettet designes omkring formationsinstancing, LOD og culling fra første prototype.

| Område | Teknisk retning |
| --- | --- |
| Soldater | GPU/animation instancing, shared rigs, LOD, pooled entities, formationsslots. |
| Pathfinding | Hierarkisk: formation route + local formation fitting; ikke NavMeshAgent per soldat. |
| Combat | Batch/aggregate resolution pr. fire group med repræsentative visuals. |
| Smoke | GPU particles/VFX + coarse simulation field til LOS-effekt. |
| Terrain | Streaming/chunking, impostors og selective detail. |
| UI | Virtualized lists til store OOB-træer og rapporter. |
| Scalability | Render ratio 1:5, 1:10, 1:20, 1:50 efter hardware; simulation forbliver identisk. |

## 25. UI/UX

UI skal gøre en kompleks simulation forståelig. Standardvisningen viser få klare indikatorer; detaljer åbnes via drill-down. Spilleren skal kunne forklare “hvorfor skete dette?” uden at læse debuglogs.

- OOB tree med commander portraits/ikoner, styrke, readiness, supply og order status.
- Map overlays: supply, command, intel, movement, rail, political control, weather.
- Order composer med mission, objective, intent, restrictions og autonomy.
- Message center med severity, source, timestamp og jump-to-location.
- Battle UI med formation card, weapon/range info, morale/cohesion/fatigue og visible command delays.
- After Action Report med timeline, losses pr. enhed, captured materiel, commander performance og map trace.

## 26. Save, replay, modding og data

Spillet bør være data-drevet fra begyndelsen. Historiske OOB’er, officerer, våben, uniformsvariationer, events og scenario-starts skal ligge i versionerede datafiler/ScriptableObjects med stabile IDs.

- Savegames serialiserer simulation state via stable IDs; visual GameObjects er ikke authoritative state.
- Deterministic seed + event log kan muliggøre replay/debug af større hændelser.
- Modding bør mindst understøtte OOB, officers, units, weapons, events, localisation og scenarios uden recompilation.
- Senere kan map data og 3D-assets åbnes mere, men det kræver en separat editor/toolchain.

## 27. Historisk datamodel og research-regler

Historisk præcision bør behandles som data provenance. Spillet må kunne skelne mellem dokumenteret værdi, estimeret værdi og designmæssig abstraktion. Det er vigtigt fordi OOB, mandskab, våben og positionsdata ændrer sig fra dato til dato.

- Alle historiske enheder og officerer får stable IDs, date-valid parent relations og kildereferencer.
- Strength er date-specific. Template strength og present-for-duty må ikke blandes sammen.
- Hvis kilder er uenige, gemmes research note og valgt interpretation i data repository.
- UI behøver ikke vise source metadata under normal gameplay, men editor/debug skal kunne.
